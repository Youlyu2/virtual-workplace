# 绘图开销与验证边界

场景通过 AppKit/Core Graphics 绘制。0.9.4 的控制窗口/全屏以30fps调度，桌面背景每屏15fps；一次绘制会提交整幅场景，因此多屏、主窗口和系统设置预览同时可见时，绘图与合成开销会叠加。持续动画的累计 GPU 时间也会随运行时长增加，需与实时百分比区分。

## 已完成的庭院优化

晴天白昼的庭院不需要天气调色或降水，但旧实现仍先创建两次全幅 RGBA 裁切。现在直接跳过没有绘图内容的裁切；需要调色或降水时共用一次原有遮罩。没有降低帧率、减少角色动作或改变原素材格式。

72组庭院旧算法逐像素对比通过，覆盖天气、昼夜、Retina、宽屏、镜像与屏幕偏移；120组优化前后场景哈希相同。

同一合成场景、每组300帧的离屏测量：

| 庭院条件 | 修改前 CPU 毫秒/帧 | 修改后 CPU 毫秒/帧 |
| --- | ---: | ---: |
| 晴天白昼 | 7.15 | 3.78 |
| 雨夜 | 23.51 | 17.46 |

上述分别约减少47%和26%的庭院绘制 CPU 耗时；**不能解释为整款应用的 CPU 降幅，更不能换算为实时 GPU 百分比下降**。实时 GPU 需要在解锁、相同窗口和显示器布局下分别采样。当前尚未完成该现场对比。

```sh
./scripts/test-outdoor-masks.sh
./scripts/test-outdoor-masks.sh --benchmark
```

诊断设768MiB和120秒上限，使用模拟内容且不启动实际应用。主应用、屏保宿主和系统窗口合成器分别计费，报告问题时请注明进程名、GPU百分比或累计GPU时间、显示器数量及当时哪些窗口可见。不要上传个人任务或便签内容。

## 已完成的远景遮罩裁切

现场采样还发现，房间窗户重画远景时，每帧都会把整幅远景的天空、水面 RGBA 遮罩转换成裁切。现在仅在首次载入时裁去两个遮罩的全透明外缘，再把保留的原始像素按相同画稿坐标使用。遮罩仍是原来的 RGBA 格式，两个缓存为固定大小；没有新增逐帧位图或随时间增长的缓存。

300组优化前后逐像素哈希完全一致，覆盖1×与Retina、五种天气、白昼/日落/夜晚、宽屏/镜像/偏移摄像机，以及通过真实房间玻璃遮罩的绘制。庭院优化与其原有72项逐像素检查保持独立。

在同一机器以合成场景各绘制180帧的离屏测量：

| 绘制范围与条件 | 修改前 CPU 毫秒/帧 | 修改后 CPU 毫秒/帧 |
| --- | ---: | ---: |
| 完整远景，晴天白昼 | 20.45 | 12.22 |
| 完整远景，雨夜 | 32.41 | 27.06 |
| 房间玻璃内远景，晴天白昼 | 5.66 | 3.10 |
| 房间玻璃内远景，雨夜 | 5.01 | 3.90 |

这些是远景绘制的 CPU 耗时，不能解释为整款应用、整个房间或 GPU 百分比的降幅。主窗口、桌面背景与系统屏保的实时占用仍需分别采样。

```sh
./scripts/test-backdrop-masks.sh
./scripts/test-backdrop-masks.sh --benchmark
```

此检查保留旧全幅遮罩算法作为测试参考，使用原始画稿与隔离的离屏绘制，同样设768MiB与120秒上限。

## 现场验证限制

2026-11-09已安装0.10.0并刷新用户授权的旧屏保宿主。新版系统设置缩略图显示了Agent数值姿态，新宿主映射与安装文件一致。退出系统设置后，一个视图记录停止并脱离窗口，但宿主的另一实例仍在绘制房间；因此系统通知补救和37项独立宿主生命周期检查不能作为真实多屏退出问题已解决的证据。

WindowServer负责所有窗口的显示合成，动态背景、屏保、其他应用和屏幕录制均可增加其GPU开销。短暂关闭工位背景时，残留屏保仍在绘制，活动监视器的进程行也未稳定刷新，因此本次不报告整机GPU下降百分比或将WindowServer全部负载归因于工位。真实多屏退出后的残留实例仍待进一步修复。
