# 内存问题与复验

0.9.3 修复了 Codex 实时观察器常驻运行时的内存持续增长。使用 0.9.2 或更早版本、并开启实时任务同步的用户，应更新并重新启动应用。

## 原因与修复

观察器在一个长期运行的 GCD 工作块中轮询会话索引和 JSONL。原有代码只对 IPC 消息设置自动释放池，索引扫描与日志解析产生的 Foundation 临时对象会积累到整个工作块退出后才释放。

现在每轮轮询、每次重连以及每行日志解析均及时清理临时对象。退出候选集合的会话也会从重同步记录中移除。人物和访客的透明绘图层限定到自身区域，减少全屏临时表面；该优化与后台解析问题分别验证。

## 可重复的隔离检查

```sh
./scripts/test-codex-memory.sh
./scripts/test-render-memory.sh
python3 Tests/MemoryGuardTests.py
```

Codex 检查连接合成 IPC 服务，使用临时 SQLite、远程候选索引和持续更新的 JSONL。它断言轮询和任务内容在测试结束前仍持续更新，预热后的物理内存增长不超过 16MiB，并设 768MiB 终止上限。数据和临时服务均与个人 Codex 会话隔离。

绘图检查复用 1920×1080 位图，绘制 8 位访客与 6 个模拟任务，3000 帧推进一个小时的场景时间，设 1GiB 终止上限。`--room` 可单独检查房间。`--underwater` 检查深海，与 `--room` 一起使用则检查浅海。模拟时间推进不能代替真实的一小时持续运行。

`scripts/guard-memory.py` 采样 macOS 的 `phys_footprint`，包含已压缩的内存；只看 RSS 可能遗漏这部分占用。它仅能终止自己启动的诊断子进程。`--pid` 模式始终只读：

```sh
python3 scripts/guard-memory.py --pid 1234 --limit-mib 1536 --timeout 300 \
  --interval 10 --jsonl build/live-memory.jsonl
```

上述检查使用测试数据。JSONL 指标不包含会话或便签内容；请勿上传个人状态文件或真实聊天日志。

## 已测结果与限制

相同合成负载的修复前后对比：后台观察器在第 6 秒至第 30 秒由 28.1MiB 增至 55.5MiB；修复后由 29.0MiB 保持在 28.7MiB。补强后的持续更新测试为 25.4→27.4MiB，收到 28 次日志更新和 5 个变化的远程候选。

绘图测试预热后约 56–85MiB，未观察到持续增长；24 组房间/户外、昼夜、天气和人物姿势的画面在透明图层优化前后逐字节一致。这些数值分别来自隔离组件测试，不能当作完整应用或多显示器屏保的内存承诺。

短时检查不能证明整夜或多天运行无泄漏。报告后续问题时，请记录应用版本、增长的是主应用还是屏保宿主、运行时长、物理内存曲线与复现步骤。
